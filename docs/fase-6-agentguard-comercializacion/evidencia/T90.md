## 1. Pedido y decisiones

Diseño propuesto en T89 y revisado antes de escribir código. Respuestas del
usuario (2026-09-15):

```
1  mandate_id en la respuesta, con su columna        → sí
2  404 MandateNotFound o código nuevo                 → reusar
3  cómo elige la persona                              → A: página "¿Qué agente lo compra?"
4  clave de idempotencia                              → buy-${request_key} (sin el agente)
5  RealOps manda mandate_id siempre                   → sí
6  guía y SDK                                         → guía sí, SDK sin compras
7  aviso del gasto compartido                         → sí
```

## 5. Tests nuevos, por lo que prueban

**Que no se puede usar un Mandato ajeno**

```
partner-routes  404s another partner's Mandate with the same body as one that does not exist, and never reaches the port
partner-routes  404s a Mandate of another tenant of the same partner, since it is not consent for this one
partner-routes  still answers TenantNotFound for another partner's tenant, before looking at the Mandate at all
partner-routes  400s a mandate_id that is null or not a Mandate id, without reaching the port
tenant-purchase answers an id that is not among this tenant's Mandates exactly like one that never existed
tenant-purchase refuses another tenant's row even if a directory ever handed one over
tenant-purchase refuses a Mandate this tenant signed for another of its agents
tenant-purchase looks the named id up among this tenant's Mandates only, and never records a foreign id as used
realops         refuses an agent of another account, or of another kind, without asking AgentPey
```

**Que nombrar no salta límites ni cambia de Mandato**

```
tenant-purchase goes through the named Mandate even when a newer one names the product
tenant-purchase hands on a named Mandate that does not cover the product, so checkMandate refuses it instead of another one being used
tenant-purchase refuses a named Mandate that is revoked / expired / not valid yet, though another active one covers the product   (3)
tenant-purchase is in force on the last instant of its window, the same edge listActiveMandates uses
tenant-purchase refuses the purchase with the named Mandate's reason instead of paying through the active one
tenant-purchase hands the named row to the decision layers, not the newer one that covers the product
policy-rail     counts every Mandate of the same agent against one running total
partner-routes  409s the same Idempotency-Key sent again with another Mandate, instead of buying through the second
```

**Compatibilidad y registro**

```
partner-routes  passes one of this tenant's own Mandates to the purchase port, and records it on the purchase
partner-routes  records the Mandate a refusal went through, too
partner-routes  leaves the choice to the platform when no Mandate is named, as before T90
purchases       accepts a Mandate id, and still accepts a request without one
purchases       refuses a mandate_id that is null, empty, or another kind of id
purchases       accepts a purchase recorded before T90, which went through no named Mandate
```

**RealOps**

```
with one signed agent, buys straight away, through that agent's own Mandate
an unsigned agent of the same kind does not make anyone choose
with two signed agents of the kind, asks which one, and asks AgentPey for nothing yet
buys through the chosen agent's Mandate, keyed by the form rather than the agent
choosing another agent from the same form sends the same key, and says so when AgentPey refuses it
refuses an agent of another account, or of another kind, without asking AgentPey
the product buttons carry the product through the choice, not a sentence
shows on each delivery which agent bought it
```

Los tests existentes de `selectMandateFor` y `explainMissingMandate` no se tocaron y
pasan.
