# T84 — evidencia

El despliegue público de los tres servicios en Render y la primera compra real
de punta a punta, hecha por el usuario con su propia wallet (Freighter) contra
los servicios desplegados. Ramas `cc/t84-*`, todas mergeadas a `main` con
confirmación explícita, una por una.

**Ningún secreto está copiado acá.** La clave del partner de RealOps y la cadena
de conexión de Postgres aparecieron en la sesión; se omiten a propósito.

## 3. Defectos encontrados corriendo el recorrido real

En orden de aparición. Ninguno lo detectaba la suite: todos vivían en un borde
entre dos servicios que las pruebas cubrían con dobles.

### 3.1 Clave del partner cortada (operativo, no código)

```
502 · AgentPey no aceptó la petición (InvalidApiKey): unknown or revoked api key
```

El valor cargado en Render terminaba en `…Rc`; el secreto real termina en
`…Rc-0`. Se corrigió en el panel.

### 3.2 La vigencia viajaba dentro del grant — `8d0ac1f`

```
502 · AgentPey no aceptó la petición (InvalidArguments): request body does not match the expected shape
```

`ProposedGrant` lleva `validFrom`/`validUntil` adentro para la pantalla de
revisión; `mandateGrantSchema` es estricto y no los conoce (la vigencia es
hermana de `grant` en el pedido). Arreglo: se quitan antes de mandar. Primera
prueba sobre el cliente real, que captura el cuerpo HTTP. Mismo commit: el host
de `render.yaml` (terminado en `45aaa93`).

Reintentar con **el mismo agente** dio después:

```
502 · (IdempotencyKeyConflict): this Idempotency-Key was already used with a different request body
```

Esperado: la clave es `consent-<agente>` y ya se había usado con el cuerpo
roto. Se probó con un agente nuevo. Ver § 7, pendiente.

### 3.3 `products` se colaba en la credencial — `c1f7615`

Con la consent session creada y la wallet verificada, al firmar:

```
InvalidCredential: payload does not match the AgentPass schema
```

`startConsentSession` armaba el `scope` de la credencial quitando **solo**
`payTo` del grant. T73 agregó `products` y ese lugar no se actualizó;
`scopeSchema` es estricto. Arreglo: `grantToScope` en `@agentpey/mandate`.
Después del despliegue el usuario firmó: `✓ Firmado. Mandato mdt_01M2DV3H129TZ25YN411RKWHBC.`

### 3.4 La acción propuesta no existía — `5263e5b`

```
rechazado · this credential does not permit "intent:create" · ScopeActionNotAllowed
rechazado · this mandate does not permit "intent:create"     · MandateActionNotAllowed
```

RealOps proponía `actions: ["purchase"]`; `checkScope` y `checkMandate` exigen
`INTENT_CREATE_ACTION = "intent:create"`, el valor que la guía de partners ya
documenta. El segundo rechazo vino del Mandato viejo, firmado antes del
arreglo: un Mandato anclado no se corrige, se vuelve a firmar.

### 3.5 El proceso se caía por una conexión ociosa — `7bbfa7b`

Síntoma intermitente, con los tres servicios despiertos:


nuevo con los tres calientes, y eso descartó la hipótesis. Ninguno de los seis

### 3.7 "Mis servicios" tardaba 73 s — `e841dff` y `16cf7da`


archivo como binario. Se vio en la salida del merge, no en revisión:


archivos cambiados desde `d0ba7b8`: ninguno con bytes de control.
