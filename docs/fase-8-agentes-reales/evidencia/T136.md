# Evidencia · T136 · SDK publicado en npm (`@agentpey/ucp-stellar`)

**Veredicto:** el paquete se instala desde su tarball en un proyecto vacío, fuera del monorepo, sin ninguna
dependencia privada, y el ejemplo del README (15 líneas) compró un imán real en `agentcommerce` pagando desde el rail
UCP: orden `ord_muvqqsth2fb48d4110`, pedido Shopify `19021144457522`, tx `1c2e815c…b127`, recibo con los tres checks.
El agente de AgentPey paga ahora a través del paquete (`R-21`, opción A) y sus tests de contrato pasan sin cambios.
**Falta la publicación en npm**, que espera el permiso del usuario y la organización `agentpey` en npmjs.com.

## 6. El ejemplo contra la tienda real

Sin `PAY=yes`, solo cotiza (abre un checkout, `R-10`; no mueve plata):

```
$ node buy.mjs
checkout cs_muvqoorte14858ef246106328ea6: 1.5684211 USDC to GD2MCESI2DMMOU4F2SI6ZHDZDDCN5LA7PMKUVZSKTKVGU5RLTCNIK5GN
```

La primera versión imprimía el total dividido por 100 ("14.9 CLP"), pero el peso chileno no tiene decimales: el
ejemplo imprime ahora el monto en USDC con `fromAtomic`.

Saldo del rail UCP antes, leído con `readTokenBalance` del paquete: `CBDRI5B7…D3YA 2.7684210` USDC.

La compra, **con OK del usuario**. El id del rail y la llave del dueño salen de `.env.local` dentro de la misma
línea de comandos, sin imprimirse:

$ PAY=yes RAIL_CONTRACT_ID="$(…UCP_POLICY_RAIL_CONTRACT_ID…)" RAIL_OWNER_SECRET="$(…AGENT_SECRET_KEY…)" node buy.mjs
checkout cs_muvqqgxv509f283ccc7cbb0f9c39: 1.5684211 USDC to GD2MCESI2DMMOU4F2SI6ZHDZDDCN5LA7PMKUVZSKTKVGU5RLTCNIK5GN

## 8. `/revisar` (2026-10-05)

El revisor no encontró chequeos perdidos ni reordenados en el refactor del agente. Hubo un bloqueante, cuatro
importantes y seis sugerencias. El usuario pidió corregir los 11:

| # | Hallazgo | Arreglo |
|---|---|---|
| 1 | El `maxAmount` decimal se convertía con los `decimals` que declara la tienda: con 14, "2.00" eran 2e14 unidades | La tienda que no declara 7 decimales se rechaza; el decimal se lee siempre con 7; opción `asset` (`USDC_TESTNET`) para nombrar el activo aceptado. El ejemplo la usa |
| 2 | El "falla cerrado" del agente dependía de cómo está escrito el paquete | El agente lleva su propia puerta (`reportingSigned`): firmado el pago, un error desconocido cuenta como posiblemente enviado |
| 3 | Ningún test del agente miraba el lado posterior a la puerta | Dos casos en `ucp-contract` (la conexión cae al completar; la tienda no confirma) y uno en `mcp-contract` (el gasto del día no se devuelve) |
| 4 | Cambios para el agente sin documentar; `*.localhost` rechazado | `*.localhost` aceptado (RFC 6761); el requisito se firma sin agregarle `extra`; `R-21` punto 2 dice el resto |
| 5 | zod 4.6.5 en el paquete, 4.5.4 en el agente | `~4.5.4` |
| 6 | Un `as` sobre la config del checkout | De vuelta al esquema zod (`checkoutHandlerConfigSchema`) |
| 7 | Sin relectura, el hook veía la copia de zod del checkout | Ve los bytes originales (test de identidad) |
| 8 | Una cotización guardada podía pagar en otro host | `payableQuoteSchema` exige el mismo origen; test |
| 9 | El hook podía modificar el requisito que se firma | Copia congelada del requisito y de las líneas; test |
| 10 | Huecos en los tests | `recheck: false`, id y endpoint que cambian, error propio del cliente x402, `maxAmount` ausente, `decimals: 14` |
| 11 | El test del manifiesto no miraba los imports | Escanea `src/*.ts` |

Después de los arreglos:
