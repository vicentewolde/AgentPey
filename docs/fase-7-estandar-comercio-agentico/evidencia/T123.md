- AP2 `v0.2` ya no tiene Intent, Cart y Payment (`specification.md`, "Mandates").
- `specification.md` líneas 155–157: el Checkout JWT del comercio "MUST be signed using a digital signature scheme (e.g., ECDSA) and not a deterministic signature (e.g., Ed25519)". `security_and_privacy_considerations.md` líneas 145–148 lo permite con sal.
- `open_checkout_mandate.json` exige `checkout.line_items` (`contains`); `open_payment_mandate.json` exige `payment.reference` (`contains`). De ahí `E-11`.

- El export **real** (Ed25519, llaves Stellar) y el mismo export con llaves
  P-256 de un solo uso (`iss` `urn:agentpey:ap2-cross-check:ephemeral-p256`)
  pasan los dos por `MandateClient.verify` con los modelos
  `OpenCheckoutMandate` y `OpenPaymentMandate`, y `payment.reference` es el
  `sd_hash` que calcula la propia librería.
- La copia alterada (tope de pago subido dentro del disclosure del mandato) la
  rechaza también la librería oficial, de otra forma: descarta el disclosure
  que no corresponde a ningún digest y el mandato queda vacío. El verificador de
  AgentPey lo rechaza explícitamente (`Ap2DisclosureMismatch`), como pide RFC
  9901 §7.1.
- Donde la librería exige P-256 es al seguir `cnf` para verificar el cierre del
  agente (`ap2/sdk/sdjwt/kb_sd_jwt.py:118` → `JsonWebKey`, solo EC P-256). T123
  no emite mandatos cerrados (`E-8`). Corrige lo que decía el replanteo (`E-9`).

## 7. Hecho cuando

| Criterio | Evidencia |
|---|---|
| Un Mandato real se exporta a los dos mandatos abiertos, firmados con Ed25519, y el verificador de AgentPey los acepta | Sección 2, pasos 3 y 4 |
| La librería oficial de AP2 acepta el mismo par con llaves P-256 de un solo uso | Sección 3 (y también el par Ed25519) |
| Un mandato AP2 alterado es rechazado con un error tipado | Sección 2 (`Ap2DisclosureMismatch` sobre el export real); sección 4: firma, disclosure, referencia, vencimiento, restricción desconocida, cada uno con su código |
| Una intención que el Mandato no permite no produce ningún mandato AP2 | Sección 4, `apps/agent`: venue, activo, monto (credencial y Mandato), producto, principal, agente, credencial ajena, intención vencida o alterada, credencial o Mandato revocados, límites que no llegan a un centavo |
| El diff no toca `checkMandate` ni el enforcement de `scope.limits` o `perDay` | Sección 6 |

## 8. Correcciones de `/revisar`

El subagente `revisor` y la revisión propia de las partes de firma encontraron
un bloqueante y cinco importantes; el usuario pidió corregir todo (`E-12`,
`E-13`):

| Hallazgo | Corrección |
|---|---|
| 🔴 Tope en unidades de Stellar, leído como centavos por AP2 (×100.000) | Centavos, redondeo hacia abajo (`E-12`) |
| 🟡 Disclosures de beneficiario e instrumento retenibles: listas vacías aceptadas | Toda lista de permitidos exige un elemento revelado; test |
| 🟡 `perDay` menor que `perTx` ignorado | Tope = menor de los cuatro límites; `perDay` 0 no exporta nada |
| 🟡 `cnf` elegible por quien llama; `iss` del par P-256 = DID de Stellar | Variante aparte fuera del índice, `iss` `urn:agentpey:ap2-cross-check:…` |
| 🟡 Varios pares por intención, más largos que la intención | `exp` ≤ vencimiento de la intención; la unicidad queda como brecha 14 |
| 🟡 Sin credencial ni `checkScope` (`M-4`) | Credencial verificada en la red, atada a la intención, `checkScope` (`E-13`) |
| 🟢 `vct` después de los tipos de restricción | `vct` primero; tokens intercambiados → `Ap2MandateInvalid` |
| 🟢 La ventana del par no se comparaba | `iat` y `exp` iguales en los dos, o `Ap2ReferenceMismatch` |
| 🟢 Claims `__proto__`/`constructor` | Objetos sin prototipo y `Object.hasOwn`; test |
| 🟢 Texto de terceros sin tope de largo | zod en la entrada: nombre ≤ 120, título ≤ 200, sitio URL |
| 🟢 Faltaban tests y versiones | Tests de intención vencida o alterada, activo, producto, principal; cinco versiones citadas |
